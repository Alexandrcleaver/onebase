# План 194 — Язык запросов для отчётности ERP

Дата проектирования: 2026-09-29. Основание — пробел P1-6 ревью ERP-готовности
([план 188](188-erp-readiness-review.md)); владелец 29.09.2026 включил его в первую
очередь планов. Заявки нет: маршрут плана 188.

## Контекст

Запросы — основной инструмент отчётов, проведения и обработок. Конфигурации,
перенесённые из 1С, и сам ИИ-конфигуратор пишут их на привычном языке, а компилятор
(`internal/query/query.go`) понимает его подмножество. Пробы на `examples/trade`,
`main` `e29ed568` — все падают:

| Конструкция | Что отвечает платформа |
|---|---|
| `ИЗ Документ.РеализацияТоваров.Товары` | `no such table: реализациятоваров.товары` |
| `… ПОМЕСТИТЬ ВТ …; ВЫБРАТЬ * ИЗ ВТ` | `near "поместить": syntax error` |
| `ГДЕ Ссылка В ИЕРАРХИИ (&Группа)` | `no such table: иерархии` |
| `ЗНАЧЕНИЕ(Перечисление.СтатусЗаказа.Новый)` | `no such column: перечисление.статусзаказа.новый` |
| `Номенклатура.ЕдиницаИзмерения.Наименование` | понятный отказ: «навигация по ссылке разворачивается на один уровень» |
| `… ИТОГИ СУММА(К) ПО ОБЩИЕ` | `near "итоги": syntax error` |
| `ИЗ ЖурналДокументов.Заказы` | `no such table: журналдокументов.заказы` |
| `ДОБАВИТЬКДАТЕ(Дата, ДЕНЬ, 1)`, `НАЧАЛОПЕРИОДА(Дата, МЕСЯЦ)` | `no such column: день` / `месяц` |

Кроме отсутствия самих конструкций, видна вторая беда: компилятор пропускает незнакомое
в SQL, и пользователь получает ошибку СУБД вместо «конструкция не поддерживается».
`onebase check` исполняет запросы модулей, поэтому ошибку он поймает — но с текстом,
который ни человеку, ни ИИ-конфигуратору не говорит, что делать.

Источников в языке пять (`sourcePrefix`: справочник, документ, три вида регистров),
функции переписываются подстановкой префикса и суффикса (`scalarFuncRewrites`) — без
разбора аргументов, поэтому функции с параметром-периодом так не выразить.

## Выбранный вариант

Язык расширяется **независимыми срезами**, от дешёвых к дорогим, каждый — отдельным PR
по своей группе функций компилятора. Первым идёт честный отказ: неподдерживаемая
конструкция 1С даёт ошибку компиляции с её названием, и каждый следующий срез
вычёркивает свою конструкцию из этого списка.

## Инварианты для всех срезов

1. **Безопасность результата не ослабевает.** Каждый новый источник и переход
   заполняет дескрипторы `query.Result`, по которым работают объектный RBAC
   (`Sources`), маскирование (`ProjectionFields`, `Projection`), типизация в DSL
   (`RefColumns`, `TypedColumns`, `BoolColumns`, `DateColumns`). Источник, который
   читает таблицу объекта, приносит в `Sources` этот объект и его строковую политику
   (RLS) — так же, как основной источник сейчас.
2. **Оба диалекта.** Семантика проверяется матричным тестом `dbtest.ForEachDialect`
   на SQLite и PostgreSQL; функции дат — с учётом правил часового пояса платформы
   (#1768).
3. **`onebase check` ловит ошибки до запуска:** неизвестное значение перечисления,
   несуществующий предопределённый элемент, табличная часть или журнал — ошибка
   компиляции, а не пустая выборка.

## Срезы

### Срез 0 — честный отказ

Распознавание конструкций из таблицы выше (и `ВЫРАЗИТЬ`, `ССЫЛКА`, `ТИПЗНАЧЕНИЯ`,
`УНИЧТОЖИТЬ`, `ВЫБРАТЬ … ИЗ ВТ`) и ошибка компиляции «конструкция «ИТОГИ» языка запросов
1С пока не поддерживается» вместо SQL-ошибки. Тест: каждая конструкция из списка
даёт этот текст через `onebase query` и через `onebase check` модуля.

### Срез 1 — `ЗНАЧЕНИЕ()`

`ЗНАЧЕНИЕ(Перечисление.X.Y)`, `ЗНАЧЕНИЕ(Справочник.X.<Предопределённый>)`,
`ЗНАЧЕНИЕ(Справочник.X.ПустаяСсылка)`, `ЗНАЧЕНИЕ(Документ.X.ПустаяСсылка)`.
Значение перечисления подставляется литералом того вида, в котором перечисление хранится
в колонке; предопределённый элемент — подзапросом по `_predefined_name`; пустая ссылка —
`NULL` (согласовано с планом 159, #1274). Имя проверяется по метаданным при компиляции.
Тесты: отбор по значению перечисления и предопределённому элементу на обоих диалектах;
несуществующее значение — ошибка `check`.

### Срез 2 — функции дат с периодом

`ДОБАВИТЬКДАТЕ`, `РАЗНОСТЬДАТ`, `НАЧАЛОПЕРИОДА`, `КОНЕЦПЕРИОДА` с периодами
`СЕКУНДА … ГОД`, `НЕДЕЛЯ`, `КВАРТАЛ`, `ПОЛУГОДИЕ`, `ДЕКАДА`; `ДЕНЬНЕДЕЛИ`, `ДЕНЬГОДА`,
`НЕДЕЛЯ`, `КВАРТАЛ`, `ЧАС`, `МИНУТА`, `СЕКУНДА`. Нужен разбор аргументов вызова — новый
вид переписывания рядом с `scalarFuncRewrites`, а не расширение подстановки.
Тесты: матрица «функция × период × граничная дата» (конец месяца, високосный год,
переход на летнее время там, где он есть) с одинаковым результатом на обоих диалектах.

### Срез 3 — табличная часть как источник

`ИЗ Документ.X.Товары КАК Т` → таблица `<сущность>_<тч>` (`metadata.TablePartTableName`);
поля `Т.Ссылка` (владелец), `Т.НомерСтроки` (`строка`), реквизиты ТЧ; `Т.Ссылка.Дата`.
Строки ТЧ видны, только если виден владелец: источник соединяется с таблицей владельца и
несёт его строковую политику; в `Sources` — владелец.
Тесты: выборка строк ТЧ с полями владельца; пользователь с RLS видит строки только
разрешённых документов; без права чтения владельца — отказ RBAC; маскируемый реквизит
владельца через `Т.Ссылка.<поле>` маскируется.

### Срез 4 — ссылки второго уровня и глубже

`Номенклатура.ЕдиницаИзмерения.Наименование`: цепочка `LEFT JOIN` с псевдонимом на
каждый путь (один и тот же путь соединяется один раз). Каждый переход подчиняется тем
же правилам, что первый уровень сейчас: объект перехода — в `Sources`, маскируемое поле
на любом уровне маскируется. Составное поле проходится только через `ВЫРАЗИТЬ` (план 191,
срез 2).
Тесты: три уровня на обоих диалектах; одинаковый путь в выборке и условии — одно
соединение; пользователь без права на промежуточный объект получает отказ; маскируемое
поле второго уровня замаскировано.

### Срез 5 — `В ИЕРАРХИИ`

`Поле В ИЕРАРХИИ (&Группа)` и `(&СписокГрупп)` для иерархических справочников
(`parent_id`): рекурсивный CTE внутри условия (`WITH RECURSIVE` есть в обоих диалектах).
Счета плана счетов — в плане 193 (условие счёта виртуальных таблиц).
Тесты: элементы группы на трёх уровнях вложенности; группа входит в собственную
иерархию; неиерархический справочник — ошибка компиляции.

### Срез 6 — журнал документов как источник

`ИЗ ЖурналДокументов.Заказы` → `UNION ALL` по документам журнала
(`journals/*.yaml`, `documents` + `columns`) с полями `Ссылка`, `Тип`, `Дата`, `Номер` и
колонками журнала. Права — как у формы списка журнала; срез сверяет её поведение и
закрепляет его тестом, а не выбирает заново.
Тесты: выборка из журнала двух видов документов; строковая политика одного вида
действует только на свою ветку; отбор по колонке журнала.

### Срез 7 — пакетный запрос и временные таблицы

Тексты через `;`, `ПОМЕСТИТЬ ВТ`, `ИЗ ВТ`, `УНИЧТОЖИТЬ ВТ`, `ИНДЕКСИРОВАТЬ ПО`;
`Запрос.ВыполнитьПакет()` возвращает массив результатов, `Выполнить()` — результат
последнего запроса пакета (как в 1С). Пакет исполняется на одном соединении в одной
транзакции (временные таблицы живут в соединении; на PostgreSQL соединение из пула
закрепляется на время пакета) под служебными именами, не пересекающимися с
пользовательскими. Дескрипторы безопасности — объединение по запросам пакета;
временная таблица наследует ограничения своих источников, потому что строит её
проверенный запрос. `onebase check` компилирует и исполняет пакет целиком.
Тесты: пакет из трёх запросов с двумя временными таблицами на обоих диалектах;
одновременные пакеты в двух соединениях не видят временных таблиц друг друга;
запрос пакета к запрещённому объекту — отказ всего пакета.

### Срез 8 — `ИТОГИ ПО`

`ИТОГИ [агрегаты] ПО ОБЩИЕ, Поле1, Поле2`. Итоги считаются в Go по детальной выборке,
упорядоченной по полям итогов (SQLite не умеет `GROUPING SETS`, а одна реализация на
оба диалекта проще сверять). Результат `Выполнить()` остаётся массивом строк — обход
«прямой», как по умолчанию в 1С: строки итогов идут перед своими детальными строками и
несут `ТипЗаписи` («ОбщийИтог», «ИтогПоГруппировке», «ДетальнаяЗапись») и `Уровень`.
Существующий код, перебирающий `Выполнить()` без `ИТОГИ`, не меняется.
Тесты: итоги по двум группировкам совпадают с `СГРУППИРОВАТЬ ПО` тех же полей;
общий итог; порядок строк; агрегаты `СУММА`, `КОЛИЧЕСТВО`, `МАКСИМУМ`.

### Дальше (вне плана)

`УПОРЯДОЧИТЬ ПО МоментВремени` для документов — после плана 189. Пакетные запросы и
`ИТОГИ` в наборах данных отчётов (СКД) — отдельным решением: у отчётов своя
группировка.

## Риски и откат

- **Горячий файл.** `query.go` — один из самых правимых файлов репозитория; каждый срез
  затрагивает свою группу функций, чтобы конфликты мержа оставались локальными.
- **Безопасность новых путей** (ТЧ, переходы, журналы, пакеты) — главный риск; каждый
  срез несёт тесты RBAC, RLS и маскирования, а не только выборки.
- **Откат** — срез удаляется вместе со своей конструкцией, и она возвращается в список
  честного отказа среза 0.

## Критерии завершения

- восемь проб из таблицы выполняются на обоих диалектах;
- ни одна неподдерживаемая конструкция не доходит до СУБД сырой ошибкой;
- `DEVELOPER.md` и `AGENTS.md` описывают новые конструкции.
