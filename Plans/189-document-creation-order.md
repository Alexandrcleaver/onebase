# План 189 — Порядок документов одной секунды: момент времени по порядку создания

Дата проектирования: 2026-09-29. Основание — находка Д3 ревью ERP-готовности
([план 188](188-erp-readiness-review.md)), вариант 2 выбран владельцем 29.09.2026.
Заявки нет: маршрут плана 188 — развилки решает владелец, затем отдельный план.

## Контекст

`МоментВремени()` документа — единственный способ получить остатки «до этого документа»:
так работают контроль остатков и списание партий ФИФО в `examples/trade`
(`src/утилиты.module.os`, `СписатьТоварыФИФО`) и в каждом модуле проведения, который
вызывает `Остатки(&МоментВремени)`.

Граница «строго до момента» сейчас строится так
(`internal/query/query.go`, `momentTimeCondition`; для регистра бухгалтерии —
`accountMomentCondition`):

```sql
(period < $P OR (period = $P AND recorder != $Документ))
```

Внутри одной секунды документы не упорядочены: каждый видит движения **всех** остальных
документов этой секунды, кроме себя. Следствия:

- итог ФИФО, резервов и средней себестоимости зависит от порядка проведения, а не от
  данных: документ A, проведённый после B той же секунды, видит расход B, а
  перепроведённый первым — не видит;
- «перепровести по порядку» не даёт воспроизводимого результата: порядка нет;
- с датой без времени (#1169) одна «секунда» — это весь день, и неупорядоченными
  становятся все документы дня.

Вывод сделан по коду и сверен с `main` `e29ed568`; воспроизводящий тест — часть среза 3.

## Выбранный вариант

Порядок `(period, порядок создания)`. У каждого документа появляется неизменяемый
номер создания `_seq` — глобальный для всех видов документов, монотонный, выдаётся при
первой записи строки. Каждое движение несёт номер создания своего регистратора. Граница
момента становится полным порядком:

```sql
(period < $P OR (period = $P AND recorder_seq < $S))
```

где `$S` — номер создания документа, чей момент передан. Отвергнутые варианты
(«по UUID, как в 1С» и «оставить, описать границу») разобраны в плане 188.

## Наблюдаемая семантика и инварианты

1. **Полный порядок.** Для двух разных документов ровно один «раньше»: сначала по
   `period` движений, при равенстве — по `_seq`. Документ видит движения только тех
   документов той же секунды, которые **созданы раньше него**, и никогда — свои.
2. **Неизменяемость.** `_seq` выдаётся один раз — при вставке строки документа — и больше
   не меняется: ни правкой, ни сменой даты, ни перепроведением, ни пометкой удаления.
   Поэтому копия номера в движениях никогда не устаревает.
3. **Глобальность.** Номер общий для всех видов документов: в один регистр пишут
   документы разных видов, и порядок внутри секунды должен сравнивать их между собой.
4. **Смена даты.** Документ, перенесённый на другую секунду, встаёт в неё по своему
   старому `_seq`: «создан раньше — раньше» сохраняется и после переноса.
5. **Несохранённый документ.** Момент документа, строки которого ещё нет в базе
   (форма до первой записи), лежит **после** всех документов своей секунды: он будет
   создан последним. Сейчас такой момент тоже видит всех соседей по секунде — поведение
   для него не меняется.
6. **Момент без документа** (`period <= $P`) и `Остатки(&Дата)` не меняются.
7. **Опорные остатки свёртки** (`RollupRecorderType`, `storage/rollup.go`) имеют номер 0 —
   раньше любого документа своей секунды.
8. **Один источник периода.** Период момента берётся по тому же правилу, что и период
   движений (`entityservice.SetPeriodFromFields` — первое поле-дата документа). Сейчас
   `runtime.Object.CallMethod("моментвремени")` ищет поле по имени
   (`дата/date/период/period`), и у документа, чьё первое поле-дата названо иначе, момент
   и движения расходятся. Срез 3 сводит оба пути к одному правилу.

### Что меняется для пользователя

Документ перестаёт видеть движения документов той же секунды, созданных **позже** него.
Конфигурация, которая создаёт документы одной секунды в обратном логическом порядке
(сначала расход, потом приход) и проводит их, получит «недостаточно остатков» там, где
раньше проходила. Это и есть исправление: прежний успех зависел от порядка проведения.
Изменение описывается в `CHANGELOG.md` и заметке релиза.

## Хранилище

| Таблица | Колонка | Тип | Смысл |
|---|---|---|---|
| документ `<entity>` | `_seq` | `BIGINT NOT NULL DEFAULT 0` | порядок создания |
| регистр накопления `рег_*` | `recorder_seq` | `BIGINT NOT NULL DEFAULT 0` | `_seq` регистратора |
| регистр бухгалтерии `акк_*` | `регистратор_порядок` | `BIGINT NOT NULL DEFAULT 0` | то же (имена колонок `акк_*` русские) |

Регистры сведений колонку не получают: первичный ключ `(period, измерения)` не допускает
двух записей одной секунды по одному набору измерений, упорядочивать внутри секунды
нечего.

**Счётчик.** PostgreSQL — последовательность `_ob_document_seq` (`nextval` не держит
блокировку до коммита; пропуски после отката допустимы). SQLite — строка в `_sequences`
с зарезервированным ключом `~document_seq` (`storage/seq.go`, `NextNum`; писатель в
SQLite один, так что строковый счётчик там не узкое место, а `~` не встречается в
именах объектов). На PostgreSQL `NextNum` не годится: строковый счётчик держит
блокировку строки до конца транзакции и выстроил бы в очередь все создания документов.

**Выдача.** В `storage.upsertInTx` (`crud.go`) — единственной точке вставки строк сущности:
если строки нет (`isNew`), колонка `_seq` получает следующее значение и входит в список
`INSERT`, но не в `ON CONFLICT … DO UPDATE SET`. Проигравшая гонка вставки сжигает номер
(пропуск), но чужой номер не перезаписывает. `UpsertVersioned` только обновляет
(`optimistic_lock.go`) и номер не трогает.

**Запись в движения.** `writeMovementsInTx` (`register.go`) и `writeAccountMovementsInTx`
(`accountreg.go`) один раз на вызов читают `_seq` регистратора из таблицы
`metadata.TableName(recorderType)` той же транзакцией (строка документа к этому моменту
уже вставлена прелюдией проведения) и пишут его в каждую строку. Тип
`RollupRecorderType` даёт 0. Отсутствие колонки или строки — ошибка записи движений,
а не молчаливый 0: так пропуск регистратора виден сразу. Номер читается в storage, а не
передаётся вызывающими: путей записи документа три (план 132), и параметр, забытый в
одном из них, вернул бы «ничей» порядок.

**Условие момента.** `momentTimeCondition` и `accountMomentCondition` получают номер
подзапросом по первичному ключу — он вычисляется один раз, а не на строку:

```sql
(period < $P OR (period = $P AND recorder_seq <
    COALESCE((SELECT _seq FROM <документ> WHERE id = $Д), 9223372036854775807)))
```

`COALESCE` реализует инвариант 5. Таблица документа берётся из `MomentTime.DocType`
только после проверки, что это документ конфигурации; иначе — прежнее условие, как
сейчас при невалидном UUID.

## Совместимость и миграция

Миграция идёт при старте, как остальная реструктуризация: документы — в `DB.Migrate`,
движения — в `MigrateRegisters` и `MigrateAccountRegisters`, которые вызываются после
него (номера регистраторов к этому моменту уже выданы).

1. Колонки добавляются `AddColumnIfMissing` с `NOT NULL DEFAULT 0` (на PostgreSQL 11+ —
   без перезаписи таблицы).
2. **Документы.** Строки с `_seq = 0` получают номера одним проходом по всем таблицам
   документов в порядке: время события «создание» из журнала регистрации (`_audit`,
   `action = 'create'`), затем `id`. Документы без такой записи идут **первыми**: журнал
   обычно включают позже, чем начинают вводить документы. Точного порядка создания
   старых документов база не хранит; это лучшее доступное приближение, и оно
   детерминировано. После прохода счётчик выставляется не ниже максимума `_seq`.
3. **Движения.** Для каждого регистра и каждого `recorder_type`, встреченного в таблице:
   `UPDATE … SET recorder_seq = (SELECT _seq FROM <документ> WHERE id = recorder)`.
   Каждая таблица — отдельной транзакцией с отметкой в `_settings`, поэтому прерванная
   миграция продолжается с места остановки, а повторный старт не делает полный проход.
   Движения без регистратора (сироты) остаются с 0 — «раньше всех в своей секунде»,
   детерминированно и видимо, а не исключены молча.
4. **Сверка счётчика при каждом старте.** Каждый `Migrate` поднимает счётчик до
   максимума `_seq` по документам: иначе новый документ получил бы номер меньше уже
   существующих и встал бы в их секунде «раньше».
5. **Восстановление из копии.** Универсальная копия выгружает таблицы целиком
   (`SELECT *`), поэтому `_seq` и `recorder_seq` переносятся как обычные колонки, а
   счётчик в копию не входит. Но импорт вызывает `Migrate` **до** загрузки строк
   (`internal/backup/universal.go`, `ImportUniversalWithOptions`), и шаги 2–4 при нём
   видят пустые таблицы. Поэтому импорт после загрузки данных вызывает ту же процедуру
   нумерации и сверки счётчика. Копии старого формата (без `_seq`) нумеруются ею же.
6. **Обмен.** Номер локален для базы: документ, пришедший по обмену, получает номер при
   первой вставке у получателя. Порядок документов одной секунды в разных узлах может
   различаться — как и сейчас различается порядок их проведения.

Цена на объёме: шаг 3 — один проход по каждому регистру. Срез 2 измеряет его на
миллионе движений SQLite и PostgreSQL и пишет цифру в заметку релиза.

## Срезы

Каждый срез — отдельный PR, тесты идут через публичные точки входа (запись и проведение
через `entityservice.Save` и DSL `Документы.X`, `onebase procrun`, `DB.Migrate`), SQL —
матричным `dbtest.ForEachDialect`.

### Срез 1 — номер создания документа

`_seq`, счётчик, выдача при вставке, миграция существующих строк, сверка счётчика.
Поведение запросов не меняется.

Тесты:
- документы двух видов, созданные подряд в одну секунду формой и DSL, получают строго
  возрастающие `_seq`; правка, перепроведение и смена даты номер не меняют;
- база, созданная без колонки, после `Migrate` получает номера по журналу регистрации,
  документы без записи в журнале — первыми; повторный `Migrate` номера не меняет;
- восстановление из универсальной копии сохраняет номера, а следующий созданный документ
  получает номер больше максимального; копия без колонки `_seq` после импорта
  пронумерована без повторного `Migrate`;
- реквизит с именем `_seq` отвергается проверкой конфигурации;
- PostgreSQL: параллельные создания из нескольких горутин получают различные номера.

### Срез 2 — номер регистратора в движениях

`recorder_seq`, `регистратор_порядок`, запись при проведении, миграция существующих
движений с отметкой прогресса, замер прохода на миллионе строк.

Тесты:
- проведение пишет в каждую строку регистра накопления и бухгалтерии номер своего
  документа, перепроведение его сохраняет; опорные строки свёртки — 0;
- движения базы, созданной до среза, получают номера регистраторов после `Migrate`;
  прерванная миграция продолжает с отмеченной таблицы;
- регистратор без колонки `_seq` даёт ошибку записи движений, а не 0.

### Срез 3 — момент времени по порядку создания

Новое условие в обеих функциях, одно правило периода момента, документация.

Тесты (все — через модуль проведения с `Остатки(&МоментВремени)`):
- приход 10 и два расхода той же секунды по 6: расход, созданный первым, проходит при
  любом порядке проведения, второй получает «недостаточно остатков» — тоже при любом
  порядке. На `main` результат зависит от порядка — тест фиксирует это до правки;
- ФИФО из `examples/trade`: перепроведение документов одной секунды в прямом и обратном
  порядке даёт одинаковые движения партий;
- регистр с итогами (`totals.enabled`) и без них, регистр бухгалтерии — один и тот же
  результат;
- момент несохранённого документа видит все документы своей секунды;
- документ, чьё первое поле-дата названо не `Дата`, получает момент в той же секунде,
  что и свои движения.

## Риски и откат

- **Изменение поведения** (раздел «Что меняется для пользователя»). Срез 3 — единственный
  переключатель; его откат возвращает прежнее условие, колонки срезов 1–2 остаются
  безвредными.
- **Длительность миграции** на больших регистрах — прогресс по таблицам, замер в срезе 2.
- **Путь записи в обход `upsertInTx`.** Если появится вставка строк документа мимо него,
  документ получит 0 и встанет первым в своей секунде. Тест среза 1 проверяет номер на
  всех путях записи (форма, DSL, REST), а сверка счётчика не зависит от пути.

## Критерии завершения

- все пути записи документа выдают `_seq`; все движения регистров накопления и
  бухгалтерии несут номер регистратора;
- результат `Остатки(&МоментВремени)` не зависит от порядка проведения документов одной
  секунды на SQLite и PostgreSQL;
- `DEVELOPER.md` описывает порядок документов, `CHANGELOG.md` — изменение поведения.
